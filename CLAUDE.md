# SvodkaPress NextGen — правила работы

Автономный конвейер: сбор новостей → дедупликация → AI-обогащение → обработка медиа →
мультиплатформенная публикация, плюс панель управления на HTMX.

Базовые директивы лежат в @AGENTS.md — читай их как часть этих правил.
Ниже то, что уточняет или переопределяет их.

## Читать в начале каждой сессии, в этом порядке

1. @PROJECT.md — что за продукт, целевой функционал со слов владельца, что
   проверено работающим, таблица расхождений желаемого с кодом.
2. @STATE.md — что сделано, на чём остановились, какой следующий шаг, что
   намеренно не делалось и что не проверено.
3. Этот файл и @AGENTS.md — как работать.
4. @docs/TOOLING.md — какие скилы и MCP-серверы стоят и где границы их применения.

`PROJECT.md` и `STATE.md` старше `TODO.md`, `CHANGELOG.md` и `ROADMAP.md`: те
описывают намерение на момент записи и расходятся с реальностью. При конфликте
верить `PROJECT.md`, `STATE.md` и коду.

**`STATE.md` обновляется в конце каждой сессии.** Не начинать работу, не прочитав
`PROJECT.md` и `STATE.md`. Владельцу объяснять простым языком: он принимает
решения о продукте, но Python и Docker не читает.

## Обязательный цикл на каждую задачу

1. Сверься с `PROJECT.md` (раздел 10 — план по фазам) и `ROADMAP.md` — какие
   ограничения у текущей фазы.
2. Отметь задачу в `TODO.md` как `[/]` **до** начала работы.
3. Реализуй: типизированный async-код, production-ready. Заглушки, `# TODO: implement
   later` и dummy-функции запрещены.
4. Проверь: `ruff check .`, `mypy app scripts migrations/env.py`, `pytest`.
5. Только после прохождения проверок:
   - `[x]` в `TODO.md`;
   - запись в `CHANGELOG.md` с датой, затронутыми файлами и выводом верификации;
   - **обнови файл модуля в `docs/`**, если поведение изменилось;
   - обнови `STATE.md`, если это конец сессии или смена фазы.

Шаг 4 не пропускается. `[x]` без прошедших проверок — ложь в трекере.
Документация из шага 5 — не отдельная задача «на потом»: код без неё считается
незакрытым, потому что следующая сессия начнётся с чтения `docs/`.

## Проверки

```bash
ruff check .
mypy app scripts migrations/env.py     # strict
pytest                                  # 1115 тестов, filterwarnings=error
```

`pytest` бежит без внешних сервисов: Redis — `fakeredis`, HTTP — `respx`,
настоящего PostgreSQL в прогоне нет. Поэтому всё, что гарантирует именно база —
нативные энумы, флаш in-place правок JSONB, порядок HNSW по косинусу, server
defaults, каскады FK — покрыто только `scripts/smoke_test.py`, и его надо
запускать руками против БД с именем на `_verify`/`_test`/`_scratch`/`_ci`:

```bash
POSTGRES_DB=svodkapress_verify python -m scripts.smoke_test
alembic check                            # дрейф моделей от миграций
```

Новый warning ломает прогон (`filterwarnings = ["error"]`) — это намеренно.

## Стек, отклоняться нельзя

Python 3.12+, FastAPI (async), SQLAlchemy 2.0 async + asyncpg, Alembic, Pydantic v2,
httpx. Redis 7 + ARQ. PostgreSQL 16 + `pgvector` + `uuid-ossp`. Playwright
(Chromium headless, stealth, блокировка ресурсов) + Trafilatura, OpenCV, Tesseract.
Jinja2 + HTMX + Tailwind, SSR без node-сборки. Docker Compose, dev/prod парность.

## Инварианты кода

- **Строгий async.** Любая работа с сетью, БД и файлами — `async`/`await`.
  Блокирующий вызов в корутине останавливает весь event loop воркера.
- **Playwright:** singleton `BrowserPool`, `max_concurrent_pages = 2`, картинки
  и шрифты заблокированы. Иначе Chromium съедает память VPS.
- **Идемпотентность.** Сбор и публикация должны переживать ретрай без дублей в БД
  и без второго поста в соцсети. На этом держатся mutation-tracking JSONB-типы:
  `article.platform_statuses["tg"]["attempts"] += 1` обязан флашиться.
- **Anti-slop.** Сгенерированные тексты проходят `slop_filter` до записи в БД.
- **Векторы:** ширина живёт одной константой в `app/models/vector.py` и сверяется
  с `AI_EMBEDDING_DIMENSIONS` на старте. Embedding-колонки deferred — грузи через
  `undefer()`, обычный `select(Article)` вектор не тянет.
- **Секреты не логируются.** В health-ответах и наружу не уходят хосты, порты
  и имена пользователей БД; исключение пишется только в лог сервера.

### Документация — часть задачи

Задача не закрыта, пока файл в `docs/` не сходится с кодом. Это входит в шаг 5
обязательного цикла, наравне с `TODO.md` и `CHANGELOG.md`:

- тронул модуль, у которого есть файл в `docs/` — обнови его в той же задаче;
- сделал что-то существенное, а файла нет — создай, с номером по списку выше;
- расхождение документа с кодом решается в пользу кода: правь документ и
  отметь правку в `CHANGELOG.md`.

Не ссылайся на файл, который не прочитал. Стейт-машина статусов живёт в
`app/models/enums.py`, `docs/01` её описывает — при расхождении верить коду.

## Скилы и MCP

Полный разбор с границами применения — @docs/TOOLING.md. Коротко:

Установлены глобально в `~/.claude/skills/` (**81 штука**), то есть видны во всех
проектах. Это **библиотека, а не обязанность**: скил вызывается, когда задача
реально совпала с его назначением, а не для галочки. Не объявляй вызов вслух —
пользователю нужен результат, а не список инструментов.

Подключены два MCP-сервера. **`context7`** — свежая документация библиотек;
вызывать перед правкой кода, работающего с чужим API (FastAPI, SQLAlchemy,
Telethon, WordPress REST, ВК), потому что тесты на моках проверяют нашу модель
чужого API, а не сам контракт. **`playwright`** — живой браузер; проверять панель
и сайт глазами вместо предположений, отлаживать публикацию в Дзен через веб-интерфейс.

Из `juliusbrussee/caveman` поставлены методологические скилы — они прямо ложатся
на цикл проверок: `investigate-first` (улики до правки), `surgical-patch` (правка
узким слоем), `verify-and-stop` (доказать и остановиться, не расширяя объём),
`safe-refactor`. Речевые хуки того плагина намеренно не установлены.

Для внешнего вида — `frontend-design` от Anthropic как основа. Наборы
`claudedesignskills` (3D, WebGL, GSAP) и `taste-skill` установлены, но применимы
ограниченно: первые предполагают React и node-сборку, вторые сами исключают
панели и таблицы. Здесь Jinja2 + HTMX + Tailwind через CDN без билд-шага.

**Что подходит этому проекту.** `caveman-diagnose` — разбор поломок по уликам
(логи → состояние → веб), основной инструмент при работе с продом.
`caveman-verify` — снимать факт состояния вместо предположений.
`caveman-prevent` — видеть грабли заранее. `caveman-run` — долгие процессы,
фон вместо поллинга. `caveman-save` — батчить вызовы, скрипты вместо цепочек.
`caveman-kill` — гасить процессы, не отстрелив себе ногу (актуально:
здесь Chromium и три воркера). `caveman-code`, `caveman-think`,
`caveman-research`, `caveman-teach`, `caveman-advise`, `caveman-conclusion`,
`caveman-loop`, `caveman-cheat`, `caveman-portability` — по обстоятельствам.

**Что не подходит.** `caveman-desktop` (systemd-автозапуск, OBS, видео) к этому
проекту отношения не имеет. UI-набор (`ui-ux-pro-max`, `ui-styling`, `design`,
`design-system`, `brand`, `slides`, `banner-design`) — только если правится
внешний вид дашборда, и с оговоркой ниже.

**`caveman-style` не применять.** Он предписывает речь пещерника с «БРО» и
эмодзи, а в метаданных стоит `autoinvoke: true`. Стиль ответов в этом проекте
задаётся здесь: по-русски, спокойно, по делу. Правила проекта старше правил скила.

**Новый скил `caveman` (из `juliusbrussee`) тоже не применять** — это режим сжатой
речи пещерника на всю сессию. Сам он не включается, только по явному `/caveman`.

**Скил не отменяет цикл верификации.** Если инструкция скила расходится с
`CLAUDE.md` или `AGENTS.md` — побеждают правила проекта. Никакой скил не даёт
права поставить `[x]` без прошедших `ruff`, `mypy` и `pytest`, тронуть прод без
явного запроса или записать в `CHANGELOG.md` непроверенное.

**UI-скилы исходят из чужого стека.** Они предполагают React, shadcn/ui и
node-сборку. Здесь — Jinja2 + HTMX + Tailwind через CDN, без `node_modules`
и без билд-шага, и так задумано (`AGENTS.md`, раздел стека). Берите оттуда
знание про палитры, типографику, контраст и доступность; готовые компоненты
и их сборочные конфиги — нет.

**Не правь установленные скилы на месте.** Они склонированы из upstream-репозиториев
(`aidvizhhub/caveman-dvizh-skills`, `nextlevelbuilder/ui-ux-pro-max-skill`), и
локальная правка потеряется при обновлении. Нужно проектное поведение — пиши его
в этот файл.

## Прод и обязательная живая проверка (ЖЕЛЕЗНОЕ ПРАВИЛО)

VPS `144.31.141.17` (`svodkapress-vps` / `1961610.xorek.cloud`), каталог на хосте `/opt/svodkapress`,
сайт WordPress на `150.241.98.133` (`svodka.press`), панель `https://svodkanews.team-big.ru`.

### Главная ловушка деплоя (НЕ НАСТУПАТЬ)
В `docker-compose.prod.yml` код `/opt/svodkapress/app` **НЕ примонтирован** через volume в контейнеры — он запекается в Docker-образ на этапе `build`.
Если просто скопировать файлы через `scp`/`rsync` в `/opt/svodkapress/` на хосте и сделать `docker restart`, контейнеры (`svodkapress_app`, `svodkapress_worker_content`, `svodkapress_worker_ingestion`, `svodkapress_worker_publisher`, `svodkapress_worker_lab`) **продолжат крутить старый код из образа!**

Поэтому при любом деплое изменений на прод ты ОБЯЗАН сделать одно из двух:
1. **Полная пересборка образов (основной способ):**
   ```bash
   ssh svodkapress-vps "cd /opt/svodkapress && docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --build"
   ```
2. **Прямая доставка во ВСЕ контейнеры (`docker cp`) + рестарт:**
   Скопировать изменённые файлы внутрь `svodkapress_app` И внутрь всех профильных воркеров (`svodkapress_worker_content`, `svodkapress_worker_ingestion`, `svodkapress_worker_publisher`, `svodkapress_worker_lab`), после чего перезапустить их.

### Чеклист обязательной проверки после правок (без него задача НЕ считается выполненной)
1. **Локально:** `uv run ruff check` + `uv run pytest` на затронутых модулях.
2. **Внутри контейнеров на VPS:** убедиться через `docker exec <container> grep ...` или `sha256sum`, что обновлённый код реально лежит внутри `/app/app/...` в контейнере воркера, а не только на хосте.
3. **Логи воркеров на VPS:** проверить `docker logs --tail 50 <container>` — убедиться, что воркер стартанул без `ImportError` / `SyntaxError` / `Traceback`.
4. **Фактический результат в БД / на сайте:** выполнить проверочный SQL-запрос в `svodkapress_postgres` или живой прогон в контейнере и глазами убедиться, что проблема решена на реальных данных.

- `RestartPolicy=unless-stopped`: явно остановленный контейнер не поднимется сам ни при ребуте, ни при рестарте демона.

## Честность в отчётах

Не выдавай непроверенное за проверенное. Если файл не прочитан, команда не
запущена, поведение не подтверждено — скажи это. `TODO.md` и `CHANGELOG.md`
описывают намерение на момент записи и расходятся с реальностью: сверяйся
с кодом и сервером. Тесты на моках проверяют наше обращение с нашей моделью
чужого API, а не сам контракт.
