Двенадцать таблиц, четыре нативных энума, восемь миграций. Источник истины —
`app/models/` и `migrations/versions/`; здесь объяснено, почему схема такая.

## 1. Реализовано

### 1.1 Расширения

- `uuid-ossp` — идентификаторы кластеров генерирует база (`uuid_generate_v4()`).
- `vector` — векторный поиск, **384 измерения**.

Ширина 384, а не 1536: векторы считает локальная модель fastembed
(MiniLM-L12-v2) на сервере, бесплатно и без сети. Ширина живёт одной константой
в `app/models/vector.py` и сверяется с настройкой при старте, иначе несовпадение
проявилось бы как ошибка запроса в рантайме.

### 1.2 Таблицы

### 1.3 Ключевые решения

**`sources`.** Уникальна пара (тип, идентификатор), поэтому один и тот же канал
нельзя завести дважды. Хранит стратегию медиа, правила разбора сайта, водяной
знак последнего сбора (`last_scraped_at`), счётчик собранных постов, аватар
как data-URI, для Telegram — тип диалога (`peer_kind`), username, описание и
публичную ссылку (`invite_link`).

**`raw_news`.** Уникальна пара (источник, внешний id поста) — на этом держится
безопасность повторного сбора: повтор просто ничего не вставит. Отдельный
частичный индекс по необработанным постам, GIN по сущностям, индекс по исходу
дедупликации. Отпечаток MinHash хранится массивом чисел.

Ссылка на кластер — `ON DELETE SET NULL`: удаление кластера не должно уносить
собранный пост.

**`news_clusters`.** UUID вместо счётчика, потому что кластер создаётся до
записи в базу и его идентификатор нужен раньше вставки. Держит рубрику, уровень
риска, обогащение (JSONB), вектор и признак публикации. HNSW-индекс по косинусу
для поиска похожих, частичный индекс по неопубликованным для очереди.

**`articles`.** Ссылка на кластер `ON DELETE CASCADE` и NOT NULL, поэтому
удаление кластера удаляет статью — именно об этом предупреждает сброс очереди,
и поэтому кластеры со статьями при сбросе сохраняются. Уникальны `url_slug` и
`wp_post_id`: первый — страховка от второй публикации одного события, второй —
от привязки двух статей к одному посту на сайте.

`platform_statuses` (JSONB) — карта площадок с состоянием, попытками, внешним
id, ссылкой и ошибкой. Тип с отслеживанием изменений: правка «на месте» вида
`statuses["tg"]["attempts"] += 1` обязана сохраняться, иначе повтор потерял бы
счётчик и мог отправить второй пост. По полю есть GIN-индекс.

`final_embedding` и `news_clusters.embedding` отложены по умолчанию: около 25 КБ
на строку, и обычная выборка статей их читать не должна.

**`article_journals`.** Компактный индекс, а не копия артефактов. Ссылка на
статью `ON DELETE CASCADE`, уникальный `run_id`, индексы по
`(article_id, started_at)` и `(cluster_id, started_at)`. Большие промты остаются
файлами в `storage/runs/<run_id>/`.

**`wp_tags_cache`.** Уникальный **функциональный** индекс по `lower(tag_name)`:
теги на сайте регистронезависимы, и без него «Москва» и «москва» создали бы два
термина. `wp_id` тоже уникален.

**`system_settings`.** Ключ — строка, значение — JSONB. Здесь живут: учётные
данные администратора, маршрутизация моделей, цепочки резерва, переключатель
конвейера и интервал сбора. Это механизм, через который настройки уезжают из
кода в панель.

**`telegram_accounts`.** Строка сессии хранится **зашифрованной** (Fernet).
Уникален номер телефона. Есть время последнего использования, штраф
флуд-ожидания и счётчик неудач — на этом работает ротация аккаунтов.

**`category_prompts`.** Переопределения промтов рубрик из панели. Ключ — `slug`
(тот же, что в `articles.category`). Поля: `title`, `voice`, `lead`, `avoid`,
`structure`, опционально `wp_term_id` (пока сайт не подключён), флаг `is_custom`
(кастомная рубрика vs переопределение встроенной). При генерации и модерации
загружаются переопределения и применяются поверх встроенных промтов; кастомные
рубрики добавляются в enum модератора.

**`ai_usage`.** Учёт токенов и расходов на вызовы LLM. Поля: `role` (arbiter /
writer / seo), `model`, `prompt_tokens`, `completion_tokens`, `total_tokens`,
опционально `cost_usd` (если шлюз вернул), опционально `cluster_id` и
`article_id` для связи с материалом. Внешних ключей нет намеренно: удаление
кластера или статьи не должно терять запись о потраченных токенах.

### 1.4 Нативные энумы

`source_type`, `media_strategy`, `risk_level`, `article_status`, `dedup_status`.

Метки в базе — это **значения**, а не имена членов (`telegram`, не `TELEGRAM`).
SQLAlchemy по умолчанию пишет имена, поэтому во всех определениях указан
`values_callable`. Ошибиться здесь — значит получить рассинхронизацию DDL и
кода, которая проявится только на реальной базе.

### 1.5 Миграции

| Миграция | Что делает |
| --- | --- |
| `0001_initial_schema` | расширения, таблицы, энумы, индексы |
| `0002_ingestion_dedup_fields` | поля исхода дедупликации |
| `0003_telegram_accounts` | таблица аккаунтов |
| `0004_spec_alignment` | вектор 1536 → 384 с пересборкой HNSW, замена энума риска, `media_planned`, новые поля `sources` |
| `0005_article_journals` | таблица `article_journals` |
| `0006_source_dialog_fields` | `sources.peer_kind`, `username`, `description`, `invite_link` |
| `0007_category_prompts` | таблица `category_prompts` |
| `0008_ai_usage` | таблица `ai_usage` |

Текущая версия в коде — `0008_ai_usage`. На сервере развёрнута `0008_ai_usage`.

### 1.6 Проверка

Тесты идут без настоящего PostgreSQL: Redis подменяется `fakeredis`, HTTP —
`respx`. Поэтому всё, что гарантирует именно база, проверяется отдельно и руками:

```bash
POSTGRES_DB=svodkapress_verify python -m scripts.smoke_test
alembic check
```

`smoke_test` защищён от запуска по продовой базе: имя должно заканчиваться на
`_verify`, `_test`, `_scratch` или `_ci`. `alembic check` ловит расхождение
моделей и миграций.

## 2. Запланировано (в коде отсутствует)

### 2.1 Каталог рубрик и теги в базе (Фаза 1)

Сейчас 20 рубрик и номера их терминов зашиты в `app/services/categories.py` под
`svodka.press`. Нужна таблица, наполняемая с подключённого сайта: на другой
установке сайт другой и номера другие. Это прямой дефект тиражируемости.

### 2.2 Промты в базе (Фаза 1)

Промты рубрик уезжают из кода в базу с правкой из панели. Вариант хранения —
отдельная таблица либо ключи в `system_settings`; выбор за проектированием Фазы 1.

### 2.3 Учётные данные площадок и аналитики (Фаза 1)

Доступы к WordPress (SSH и REST), соцсетям и аналитике хранятся в базе
шифрованно, как уже сделано для строки сессии Telegram. Значения из `.env`
перестают быть источником истины.

### 2.4 Признак проекта (решено: не делаем)

Мультипроектность через `project_id` в таблицах **не вводится**: одна установка
обслуживает один сайт, для второго проекта разворачивается вторая копия со своей
базой. Схема остаётся плоской, тиражируемость обеспечивается настройками в базе.

### 2.5 Состояние ручного режима (Фаза 2)

Слой одобрения потребует хранить, на каком шаге материал ждёт решения и что
владелец уже подтвердил. Текущего набора статусов для этого мало.
