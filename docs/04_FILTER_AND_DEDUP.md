# 04_FILTER_AND_DEDUP.md — Фильтр и дедупликация (Module 2.2)

## Назначение и место в конвейере
Второй шаг конвейера (`docs/01_DATA_PIPELINE.md`, **DEDUPLICATED**). Задача модуля — отсеять мусор и повторы **до** того, как новость попадёт в дорогие AI-стадии Package 3. Экономика простая: всё, что можно решить эвристикой и локальными вычислениями, решается за **0 токенов**; LLM привлекается только к реально спорным случаям.

Порядок обработки строки `raw_news`:
1. Эвристический фильтр (`app/services/text_utils.py`) — 0 токенов.
2. Дедупликация в три уровня (`app/services/deduplicator.py`) — 0 токенов на первом уровне.
3. Фиксация исхода в `raw_news.dedup_status`.

## Эвристический фильтр (`app/services/text_utils.py`)

### Telegram entities → HTML
Telegram отдаёт форматирование отдельным массивом `entities` с офсетами, а не разметкой в тексте. Конвертер поддерживает:

| Entity | HTML |
| --- | --- |
| `bold` | `<b>` |
| `italic` | `<i>` |
| `underline` | `<u>` |
| `strikethrough` | `<s>` |
| `spoiler` | `<span class="tg-spoiler">` |
| `code` | `<code>` |
| `pre` | `<pre><code>` |
| `text_link` | `<a href="...">` |
| `url` | `<a href="...">` (href = сам текст) |
| `blockquote` | `<blockquote>` |

**Требование корректности: офсеты и длины Telegram заданы в кодовых единицах UTF-16, а не в символах Python.** Строка Python индексируется по кодовым точкам, поэтому любой эмодзи, флаг или иной символ вне BMP (занимающий 2 кодовые единицы UTF-16) сдвигает все последующие офсеты. Наивная нарезка `text[offset:offset+length]` рвёт разметку и калечит текст — теги уезжают на несколько символов, суррогатные пары разрубаются пополам.

Поэтому конвертация **обязана** выполняться в UTF-16: текст кодируется в `utf-16-le`, разметка расставляется по байтовым позициям `offset * 2` / `length * 2`, результат декодируется обратно. Это не оптимизация, а условие правильности — в русскоязычных новостных каналах эмодзи есть практически в каждом посте.

Дополнительно: пересекающиеся и вложенные entities раскладываются в корректно вложенный HTML, а текстовые фрагменты экранируются (`&`, `<`, `>`), чтобы источник не мог внедрить разметку.

### Детекция дайджестов
Дайджест («новости пачкой») бесполезен как инфоповод: он не про одно событие и генерирует ложные срабатывания дедупликации. Признаки:
- **Нумерованные перечисления:** строки, начинающиеся с `1.`, `2.`, `3.` (а также `1)` и вариант с emoji-цифрами). Порог — **3 и более** элементов подряд.
- **Заголовки-сводки:** «Главное к этому часу», «Итоги дня», «Дайджест», «Главное за», «Коротко о главном», «Что произошло за». Сравнение регистронезависимое, по нормализованному тексту.

Совпадение → `is_digest = true`, и строка получает `dedup_status = filtered_digest`.

### Детекция рекламы и спама
- **Маркеры маркировки:** `erid`, `erid:`, токены вида `erid=...` в ссылках.
- **Промокоды:** конструкции «промокод», «по коду», «скидка N%» в связке со ссылкой.
- **Реферальные и бот-ссылки:** `t.me/...?start=`, партнёрские редиректы, сокращатели (`bit.ly`, `clck.ru`, `vk.cc`, `tinyurl` и подобные).
- **Рекламные подвалы:** «на правах рекламы», «реклама», «партнёрский материал», «#промо».
- **Плотность ссылок:** число ссылок относительно объёма текста выше порога — короткий пост, состоящий в основном из ссылок, считается спамом.

Совпадение → `is_ad = true`, `dedup_status = filtered_ad`. Отфильтрованные строки не удаляются: они остаются в `raw_news` с `is_processed = true` для аудита и настройки правил.

### Обработка постов без текста (2026-09-27)
Посты с пустым текстом (`raw_text.strip() == ""`), возникающие из-за публикации медиа без подписи либо технических артефактов альбомов, не содержат фактологии для статьи:
- В модуле дедупликации `Deduplicator.deduplicate` такие посты переводятся в статус `DedupStatus.SKIPPED_DUPLICATE` с причиной `empty_text` и флагом `is_processed = true` без создания пустого кластера (`cluster_id = None`).
- Это предотвращает засорение очереди сюжетов пустыми карточками с техническими заголовками `raw_news #...`.

### Контракт результата
Фильтр возвращает **frozen dataclass** (неизменяемый результат, который дальше только читают):

| Поле | Тип | Значение |
| --- | --- | --- |
| `clean_text` | `str` | Нормализованный plain-text без разметки и служебных подвалов. |
| `clean_html` | `str` | HTML, полученный из entities. |
| `is_digest` | `bool` | Сработала детекция дайджеста. |
| `is_ad` | `bool` | Сработала детекция рекламы/спама. |
| `reasons` | `list[str]` | Имена сработавших правил (например `digest_numbered_list`, `ad_erid`, `ad_link_density`). |
| `link_count` | `int` | Количество найденных ссылок. |

`reasons` — обязательное поле, а не отладочное: без него нельзя понять, почему конкретная новость выпала из конвейера, и невозможно править эвристику по фактам. Список пишется в `raw_news.entities` под ключом `filter_reasons`.

## Дедупликация (`app/services/deduplicator.py`)

### Уровень 1 — MinHash LSH, 0 токенов
Первый и основной уровень. Работает локально, без внешних API.

1. **Нормализация:** приведение к нижнему регистру, унификация `ё`→`е`, удаление URL, эмодзи, пунктуации и стоп-слов, сжатие пробелов.
2. **Шинглы:** 3-граммы **слов** (не символов) — устойчивы к перестановке фраз и характерному для новостей рерайту заголовков.
3. **Сигнатура:** `datasketch.MinHash` с `MINHASH_NUM_PERM` перестановками (по умолчанию 128).
4. **Банды:** сигнатура разбивается на `LSH_BANDS` (32) полос; хеш каждой полосы даёт ключ корзины в Redis:

```
lsh:bucket:{band}:{hash}   ->  SET из raw_news.id / cluster_id
TTL = DEDUP_LOOKBACK_HOURS
```

TTL — единственный механизм вытеснения: Redis работает с `maxmemory-policy noeviction` (см. `ROADMAP.md`, Phase 0), поэтому индекс обязан истекать сам, а не рассчитывать на вытеснение сервером.

5. **Сравнение:** кандидаты из общих корзин сравниваются по Jaccard-оценке MinHash. `Jaccard >= LSH_DUPLICATE_THRESHOLD` (**0.85**) → **дубль**: возвращается `cluster_id` найденного совпадения, вызовов AI нет, **0 токенов**.

Сигнатура сохраняется в `raw_news.minhash_signature` (`ARRAY(BIGINT)`), поэтому после сброса Redis LSH-индекс перестраивается из базы, без повторного обращения к источникам.

Целевой бюджет уровня — **менее 5 мс** на пост (цель, а не измеренный результат). Это позволяет прогонять через уровень 1 весь поток и отдавать наверх лишь единицы процентов.

### Уровень 2 — семантический поиск pgvector
Вызывается **при неоднозначности уровня 1**: `LSH_AMBIGUOUS_THRESHOLD` (**0.40**, снижено с 0.60 для предотвращения дробления событий из разных каналов на отдельные кластеры) `<= sim <` `LSH_DUPLICATE_THRESHOLD` (**0.85**), либо при совпадении ключевых именованных сущностей (включая русские топонимы от 5 букв, авиакомпании и фамилии). Ниже 0.40 при отсутствии общих сущностей текст считается заведомо другим, выше 0.85 вопрос уже закрыт — в обоих случаях уровень 2 не запускается и токены не тратятся.

- Эмбеддинг текста строится моделью `AI_MODEL_EMBEDDING`, ширина — **384**
  (совпадает со схемой, `app/models/vector.py`). Модель локальная (fastembed
  MiniLM-L12-v2): считается на сервере, бесплатно и без сети.
- Поиск: косинусная близость к `news_clusters.embedding` по HNSW-индексу `ix_news_clusters_embedding_hnsw`, окно — `created_at >= now() - DEDUP_LOOKBACK_HOURS`.

- **Важно:** колонки эмбеддингов объявлены `deferred` (`deferred_group="embedding"`). Запрос на similarity обязан явно затребовать вектор — через `undefer(NewsCluster.embedding)` либо прямым `select(NewsCluster.embedding, ...)`. Иначе ORM выдаст ленивую подгрузку по одной строке (или `MissingGreenlet` в async-контексте).

Решение по косинусной близости:

| Косинусная близость | Решение |
| --- | --- |
| `< SIMILARITY_LOWER_THRESHOLD` (0.55) | Новый инфоповод → создаётся `news_clusters` |
| `>= SIMILARITY_UPPER_THRESHOLD` (0.76) | Тот же инфоповод → привязка к существующему кластеру |
| 0.55 .. 0.76 | Спор → LLM-арбитр |

**LLM-арбитр** (`AI_MODEL_ARBITER`, включается `DEDUP_ENABLE_LLM_ARBITER`): получает два заголовка с ключевыми фактами и обязан ответить строго `YES` или `NO` (один и тот же инфоповод или нет). Ответ парсится жёстко; всё, что не распознано как `YES`, трактуется как `NO` — ложное «новый кластер» дешевле склейки двух разных новостей. Это единственная точка модуля, где тратятся токены генерации, и она вырожденно мала: один вопрос, ответ в одно слово.

### Уровень 3 — проверка новизны (Novelty Checker)
Запускается, когда уровни 1–2 признали пост дублем существующего кластера. Вопрос уровня 3 иной: **несёт ли этот дубль новые факты?**

Извлекаемые сущности:
- даты и время («вчера», «14 марта», `2026-03-14`);
- числа и количества (пострадавшие, объёмы, проценты);
- денежные суммы с валютой (₽, $, «млрд рублей»);
- именованные сущности с заглавной буквы (персоны, организации, топонимы).

Набор сравнивается с накопленными фактами кластера в `news_clusters.enrichment_data.facts`:
- **Новых фактов нет** → дубль закрывается: `raw_news.dedup_status = skipped_duplicate`, `is_processed = true`, статья не создаётся.
- **Новые факты есть** → в `enrichment_data` дописывается дельта (`facts_delta` с ссылкой на `raw_news.id` и временем), `dedup_status = update`, кластер ставится в очередь на обновление статьи.

`enrichment_data` — mutable JSONB (`MutableJSONB`), поэтому вложенное изменение фиксируется без пересборки всего объекта.

### Таблица решений
| Уровень | Условие | Исход | Стоимость в токенах |
| --- | --- | --- | --- |
| 0 | `is_digest` или `is_ad` | `filtered_digest` / `filtered_ad` | 0 |
| 1 | Jaccard `>= 0.85` | Дубль → уровень 3 | 0 |
| 1 | Jaccard `< 0.60` | Уникум → новый кластер | 0 |
| 2 | Jaccard 0.60..0.85, cos `< 0.55` | Уникум → новый кластер | 1 локальный эмбеддинг |
| 2 | Jaccard 0.60..0.85, cos `>= 0.76` | Дубль → уровень 3 | 1 локальный эмбеддинг |
| 2 | Jaccard 0.60..0.85, cos 0.55..0.76 | Арбитр `YES`/`NO` | 1 локальный эмбеддинг + 1 короткий запрос |
| 3 | Новых фактов нет | `skipped_duplicate` | 0 |
| 3 | Есть новые факты | `update` + дельта в кластере | 0 |

## Фиксация исходов
Исход дедупликации живёт на `raw_news`:
- `dedup_status` — нативный enum PostgreSQL `dedup_status` (создаётся через `pg_enum`, как остальные enum в `app/models/enums.py`): `pending`, `unique`, `duplicate`, `skipped_duplicate`, `update`, `filtered_digest`, `filtered_ad`. Значение по умолчанию — `pending`.
- `is_ad` — булев флаг рядом с уже существующим `is_digest`, чтобы отделять рекламу от дайджестов без разбора `reasons`.
- `cluster_id` заполняется для `unique`, `duplicate` и `update`; для отфильтрованных и `skipped_duplicate` без кластера остаётся `NULL`.

**Статус `SKIPPED_DUPLICATE` из `docs/01_DATA_PIPELINE.md` записывается именно здесь, на `raw_news`, а не на `articles`.** Причина прямая: пропущенный дубль по определению не доходит до генерации, строки `articles` для него никогда не существует, и записывать его статус в `ArticleStatus` некуда. В `ArticleStatus.SKIPPED_DUPLICATE` (`app/models/enums.py`) это состояние **недостижимо** — данная спецификация закрывает эту дыру, перенося учёт на ту таблицу, где событие реально происходит.

## Деградация без AI-ключа
Если `OPENROUTER_API_KEY` не задан, модуль **не падает**:
- Уровень 2 не выполняется — эмбеддинг не построить.
- Уровень 3 не выполняется для случаев, требовавших эскалации.
- Решение принимается по результату уровня 1: неоднозначные случаи трактуются как **новый кластер**, а не как дубль (нежелательный дубликат в выдаче дешевле потерянной новости).
- Факт деградации логируется и отмечается в `raw_news.entities` (`dedup_degraded: true`), чтобы такие строки можно было позже перепроверить.

Итог: конвейер полностью работоспособен при нулевых расходах на AI. `DEDUP_ENABLE_LLM_ARBITER = false` даёт то же поведение осознанно, при наличии ключа.

| `AI_MODEL_ARBITER` | `openai/gpt-4o-mini` | Модель арбитра `YES`/`NO`. |
| `AI_MODEL_EMBEDDING` | `local/fastembed-minilm-l12-v2` | Модель эмбеддингов, **384 измерения**, локально и бесплатно. |

Пороги 0.55/0.76 откалиброваны измерением под локальную модель и намеренно
отличаются от значений спецификации (0.75/0.92), рассчитанных на другую модель.

## Решение проблемы дублирования новостей (Module 2.2 & 11.25 / 2026-10-04)

Параллельное размножение кластеров и генерация одинаковых статей блокируются четырьмя взаимосвязанными механизмами:

1. **Сквозная семантическая сверка при инжесте (`app/services/deduplicator.py`):**
   - Устранён искусственный отсев постов с `Jaccard < 0.40`. При отсутствии точного совпадения по MinHash пост проверяется через расширенный поиск именованных сущностей среди последних 250 кластеров (`_find_entity_candidate_cluster`).
   - Если сущность не выявлена, в боевом окружении запускается глубокий семантический поиск через HNSW-индекс в `pgvector` по локальным бесплатным эмбеддингам (`fastembed`, 384d). Если сходство с существующим кластером за 48 часов $\ge 0.76$, пост автоматически привязывается к кластеру без создания дубля.

2. **Кросс-статейный фильтр в генераторе (`app/workers/content_worker.py`):**
   - Функция `_find_duplicate_article` сканирует последние 500 опубликованных статей за 48 часов.
   - **Лексический стемминг с нормализацией суффиксов (`_extract_title_stems`):** выделяются нормализованные корни слов ($\ge 4$ букв с отсечением русских падежных окончаний и суффиксов прилагательных/причастий `-ск`, `-енн`, `-анн`, чтобы `Жулебинском` и `Жулебино` сводились к единому корню `жулебин`). Совпадение $\ge 3$ стемов, либо Jaccard стемов $\ge 0.35$, либо совпадение редкой сущности ($\ge 7$ букв) + 1 общего корня немедленно признаётся дубликатом.
   - **Семантический поиск pgvector:** прямой SQL-запрос косинусного расстояния по `Article.final_embedding` с порогом сходства $\ge 0.77$. Дублирующие кластеры помечаются `is_published = True` и безопасно пропускаются.

3. **Защита от параллельной гонки воркеров (`_check_and_acquire_event_lock` в Redis):**
   - Перед генерацией статьи воркер атомарно проверяет хэш `dedup:active_event_generations` в Redis (TTL 900 секунд), где хранятся активные параллельные генерации со списками их корней.
   - Если у нового сюжета пересекаются $\ge 2$ значимых корня ($\ge 4$ букв) или $\ge 1$ редкая сущность ($\ge 7$ букв, например `жулебин`) с уже идущей генерацией в другом воркере, генерация немедленно блокируется, а кластер помечается `is_published = True`.

4. **Ретроспективная зачистка дублей (`scripts/cleanup_duplicate_articles.py`):**
   - Скрипт анализирует опубликованные статьи за последние N дней, использует транзитивное объединение облака корней (`orig_stems.update(stems)`) для захвата всех вариаций одного инфоповода, сохраняет канонический оригинал, переводит дубли в базе в статус `SKIPPED_DUPLICATE` и перемещает соответствующие записи в WordPress в корзину (`trash`) через REST API.

`SIMILARITY_UPPER_THRESHOLD > SIMILARITY_LOWER_THRESHOLD` проверяется валидатором модели в `app/config.py` на старте приложения.
