# 11_DEPLOYMENT_DEVOPS.md — Развёртывание и эксплуатация

Образ, состав контейнеров, прод-конфигурация, сеть и обслуживание по SSH.

**Как читать этот файл.** «Реализовано» описано по коду и проверено на сервере.
«Запланировано» — намерение из `PROJECT.md`. При расхождении верить коду и
фактическому состоянию сервера.

Файлы: `Dockerfile`, `docker-compose.yml`, `docker-compose.override.yml`,
`docker-compose.prod.yml`, `scripts/deploy_vps.sh`, `scripts/remote_ssh.py`.

## 1. Реализовано

### 1.1 Образ

Многоступенчатый `Dockerfile` на `python:3.12-slim-bookworm`. В рантайме:
Tesseract с русским и английским, библиотеки OpenCV, Playwright Chromium, git,
клиент SSH, `tini` как init. Пользователь непривилегированный, uid 1000.

Проверка живости — `curl` на `/health` каждые 30 секунд, старт-период 40 секунд.
`/health` терпит падение Redis (это только проверка живости), а `/health/ready`
проверяет и PostgreSQL, и Redis.

### 1.2 Состав контейнеров

| Сервис | Что делает | Память (прод) |
| --- | --- | --- |
| `postgres` | PostgreSQL 16 + pgvector | 1536 МБ |
| `redis` | Очередь задач и индекс дублей | 768 МБ |
| `app` | Веб-панель и API (gunicorn + uvicorn, 2 рабочих) | 1536 МБ |
| `worker-ingestion` | Сбор новостей, Chromium | 2048 МБ |
| `worker-content` | Генерация статей и медиа | 1024 МБ |
| `worker-publisher` | Публикация и распространение | 1024 МБ |

Redis работает с политикой `noeviction`: он брокер очереди и индекс отпечатков,
а не кэш — вытеснение ключей означало бы потерю заданий.

У каждого воркера **своя очередь**: на общей очереди ARQ воркеры воровали
задания друг у друга. Проверка живости воркера — `arq --check` с интервалом 30
секунд; интервал переопределён намеренно, иначе значение по умолчанию (час)
оставляло зависший воркер «здоровым».

Dev-накладка (`docker-compose.override.yml`) публикует порты только на 127.0.0.1
и включает горячую перезагрузку; воркеров там нет.

### 1.3 Развёртывание и доставка кода в контейнеры (КРИТИЧЕСКОЕ ПРАВИЛО)

`scripts/deploy_vps.sh` идёт по порядку: проверить Docker и Compose → проверить
`.env` на незаполненные секреты → проверить конфигурацию compose → поднять →
применить миграции внутри контейнера `app` → дождаться `/health`, затем
`/health/ready` → убедиться, что все воркеры работают.

**Развёртывание идёт копированием в `/opt/svodkapress`, а не `git clone`.**

> **ВНИМАНИЕ (Ловушка образов в `docker-compose.prod.yml`):**
> В боевом `docker-compose.prod.yml` каталог `/opt/svodkapress/app` **НЕ монтируется** с хоста в контейнеры (`svodkapress_app`, `svodkapress_worker_content`, `svodkapress_worker_ingestion`, `svodkapress_worker_publisher`, `svodkapress_worker_lab`), а запекается внутрь образа при сборке!
> Поэтому простое копирование файлов на хост (`scp`/`rsync` в `/opt/svodkapress`) и `docker restart` **НЕ обновляет код внутри воркеров**.

**Обязательный регламент деплоя и проверки любого изменения:**
1. Доставить файлы на хост `/opt/svodkapress`.
2. Обновить код внутри самих контейнеров одним из двух способов:
   - **Штатная пересборка всех сервисов:**
     ```bash
     docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --build
     ```
   - **Оперативная горячая замена (`docker cp`):** скопировать файлы внутрь `svodkapress_app` и **всех** затронутых воркеров (`svodkapress_worker_content`, `svodkapress_worker_ingestion`, `svodkapress_worker_publisher`, `svodkapress_worker_lab`), после чего выполнить `docker restart` этих контейнеров.
3. **Обязательная верификация после деплоя:**
   - Проверить наличие нового кода внутри контейнера воркера (`docker exec svodkapress_worker_content grep ...` или `sha256sum`).
   - Проверить логи старта (`docker logs --tail 50 svodkapress_worker_content`) на отсутствие `ImportError`/`SyntaxError`.
   - Проверить реальный результат в БД (`docker exec -i svodkapress_postgres psql -U svodkapress -d svodkapress ...`) и на сайте (`svodka.press`).

Проверенный порядок полного копирования:

1. Дамп базы: `pg_dump | gzip` в `/opt/backups/`, затем `gzip -t` для проверки.
2. Архив текущего кода в `/opt/backups/code-*.tar.gz` — откат без пересборки.
3. `rsync` в промежуточный каталог, затем установка с исключениями `.env`,
   `secrets/`, `storage/` и **обязательно** `docker-compose.override.yml`:
   dev-накладка публикует PostgreSQL и Redis на хост, чего на публичном сервере
   быть не должно.
4. `docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --build`.

### 1.4 Прод: фактическое состояние

Сервер `144.31.141.17` (`1961610.xorek.cloud`).

**Сеть — незакрытый дефект, проверено 2026-09-03.** `ufw` включён и разрешает
8000 только адресам прокси, но цепочка `DOCKER-USER` **пуста**. Docker обрабатывает
свои DNAT-правила раньше `INPUT` в `ufw`, поэтому правила `ufw` опубликованный
порт не защищают. Внешняя проверка с рабочей машины: TCP-соединение на
`144.31.141.17:8000` и `:3005` устанавливается, приложение отвечает `400` только
потому, что срабатывает проверка `ALLOWED_HOSTS`. Прежнее утверждение в этом
документе, будто фильтрация продублирована в `DOCKER-USER` и сохранена между
перезагрузками, **не соответствует фактическому состоянию**.

Закрывается двумя правилами (требует решения владельца, потому что затрагивает
доступность прокси):

```bash
iptables -I DOCKER-USER 1 -p tcp --dport 8000 -s 150.241.98.134 -j RETURN
iptables -I DOCKER-USER 2 -p tcp --dport 8000 -s 150.241.98.133 -j RETURN
iptables -I DOCKER-USER 3 -p tcp --dport 8000 -j DROP
```
(Прокси `150.241.98.134` обслуживает домен `svodkanews.team-big.ru` через Nginx Proxy Manager, пересылая запросы на `144.31.141.17:8000`).

`RestartPolicy=unless-stopped`: контейнер, остановленный вручную, **сам не
поднимется** ни при перезагрузке, ни при рестарте демона. Все сервисы и воркеры
подняты деплоем через `scripts/deploy_vps.sh` и работают штатно.

Версии сведены: на сервере и локально — **2.10.0**, миграция
`0005_article_journals`. Судить о развёрнутом коде по `CHANGELOG.md` всё равно
нельзя: деплой идёт копированием, поэтому при сомнении сравнивать файлы.

### 1.5 Обслуживание чужого хоста по SSH

`scripts/remote_ssh.py` — узкий канал к серверу WordPress: выполнить команду,
загрузить файл, проверить место на диске, перечитать конфигурацию nginx. Для
будущего подключения добавлен `RemoteTarget`: проверяет только метаданные
(host, user, port, пути ключа/known_hosts и каталог WordPress), не хранит ключ и
не открывает соединение.

Три решения по безопасности:

- **Только аутентификация по ключу.** Ни запроса пароля, ни `ssh-agent`: скрипт,
  который можно заставить спросить пароль, — это скрипт, который однажды повиснет.
- **Ключ хоста проверяется.** Отключение требует явного флага, чьё имя говорит о
  цене. Молча принимать любой ключ — способ отдать команды тому, кто ответил на
  22-м порту.
- **Команды передаются списком аргументов**, каждый квотируется. Путь с
  пробелом или точкой с запятой остаётся данными, а не второй командой.

**Важно: конвейер этот канал не использует.** Ни один модуль в `app/` его не
импортирует; настройки `SSH_*` читает только сам скрипт. Публикация идёт
исключительно через REST, см. `docs/07`.

## 2. Запланировано

### 2.1 Публикация по SSH из конвейера (Фаза 4)

Из решения владельца: сайт подключается по SSH с доступом к файловой системе.
Нужно превратить обслуживающий скрипт в модуль публикации, вызываемый из
воркера, с доступами из базы (шифрованно), а не из `SSH_*` в `.env`.

### 2.2 Разворот второго проекта

Одна установка обслуживает один сайт (решение от 2026-09-02). Второй проект —
вторая копия контейнеров со своей базой. Признак проекта через таблицы **не
проводим**: схема остаётся плоской, а тиражируемость обеспечивается тем, что
настройки живут в базе, а не в коде. Порядок разворота нужно описать отдельной
инструкцией по установке.

### 2.3 Что нужно привести в порядок на проде

Не задачи разработки, но без них конвейер не работает:

- **закрыть порты 8000 и 3005 в цепочке `DOCKER-USER`** — сейчас они отвечают из
  интернета, см. 1.4. Это самый срочный пункт;
- включить переключатель конвейера в панели: воркеры подняты 2026-09-03, но
  `pipeline_control.enabled = false`, поэтому сбор и генерация не идут. Включение
  начнёт тратить деньги на ИИ, поэтому это решение владельца;
- заполнить доступы (после Фазы 1 — через панель, не через `.env`). Сейчас пусты
  `WP_APP_USER`, `WP_APP_PASSWORD`, `FAL_KEY`, а `WP_BASE_URL` указывает на
  панель `svodkanews.team-big.ru`, а не на сайт `svodka.press`;
- завести резервный Telegram-аккаунт: сейчас он один, и блокировка остановит
  сбор целиком.

Любая изменяющая команда на проде — только по явному запросу владельца. Чтение
логов и состояния свободно.

## 3. Проверки

```bash
bash scripts/deploy_vps.sh --check-only
docker compose config
```

Локальный прогон тестов внешних сервисов не требует: Redis подменяется
`fakeredis`, HTTP — `respx`, настоящего PostgreSQL в прогоне нет. Всё, что
гарантирует именно база — нативные энумы, флаш правок JSONB, порядок HNSW,
server defaults, каскады — проверяется отдельно:

```bash
POSTGRES_DB=svodkapress_verify python -m scripts.smoke_test
alembic check
```
